# Abstract

The ArmoniK CLI currently in development provides essential functionality with minimal dependencies. However, there are many additional tools and utilities for ArmoniK written in various languages (Python, Bash, JavaScript, etc.) that would benefit from consolidation. This AEP proposes a design for an extension system that will allow the ArmoniK community to integrate existing tools and develop new ones as extensions to the CLI, without compromising the core functionality or user experience.
# Motivation

The motivation behind this proposal is multi-faceted:

1. **Tool Consolidation**: There are numerous tools and utilities for ArmoniK scattered across different languages and repositories. Consolidating them under a single interface would improve discoverability and usability.
2. **Unified Interface**: The ArmoniK CLI already provides a standard interface that works well across different environments. Extending this interface rather than creating separate tools ensures a consistent user experience.
3. **Community Engagement**: By providing a clear pathway for the community to contribute extensions, we can encourage more active participation in the ArmoniK ecosystem.

4. **Developer Experience**: Extensions can significantly improve developer experience, such as through project bootstrapping utilities that guide users through configuration processes.

5. **Maintainability**: By separating core functionality from extensions, we can ensure that the core CLI remains stable while allowing for innovation through extensions.

# Specification

## Design Principles

The extension system is built on three key pillars:

1. **Independence**: Extensions should be versioned and maintained independently from the ArmoniK CLI. They should depend on ArmoniK.CoreCLI rather than ArmoniK.CLI directly, ensuring that changes to the CLI don't break existing extensions.

2. **Ease of Installation**: The end-user experience should never be compromised. Extensions should be easy to install and remove, which is particularly important for CI/CD environments.

3. **No Mutations to ArmoniK.CLI**: Extensions should not change the behavior of existing ArmoniK.CLI functionality. They should primarily add new commands rather than modify existing ones. Special cases like adding new serialization formats may be considered separately.

## Implementation

To support these principles, we propose splitting the current CLI into two components:

1. **ArmoniK.CoreCLI**: The foundational library that both the main CLI and all extensions will depend on.

2. **ArmoniK.CLI**: The user-facing command-line interface, which will include extension discovery functionality.

These components should be maintained and versioned in separate repositories.
## Extension Discovery

For plugin discovery, we decided to use the already existing Python entrypoints. Users only need to `pip install <extension-name>`. A proof of concept of this approach has been implemented and it serves our purposes pretty well.

Extensions will need to expose a command group or single command to our extensions entrypoint: "armonik.cli.extensions". 

The ArmoniK CLI will lazily load these extensions as is needed during execution so to minimize resource consumption.

The ArmoniK CLI will feature a command to list installed extensions.
If the extension fails to load, then we instanciate a broken extension object whenever it's executed to inform the user about it. 

All plugin configurations should be centralized within the ArmoniK config under a "Plugins" section with a mapping of plugin to plugin configuration.

## Extension Discovery

### Mechanism

For plugin discovery, this AEP specifies the use of Python's standard **entry points** mechanism, provided by the `importlib.metadata` library. This is the modern, canonical approach for building pluggable applications in the Python ecosystem.

This approach completely decouples extensions from the main CLI. Users can install an extension with a standard `pip install <extension-name>`, and the ArmoniK CLI will automatically discover it upon next execution without needing any central registration or configuration changes.

### Rationale

The entry points approach was chosen over alternatives (such as listing enabled plugins in a configuration file) for several key reasons:

1. **Standardization & Ecosystem Compatibility**: Entry points are a core feature of Python packaging. This ensures maximum compatibility with standard tools like `pip`, PyPI, and virtual environments.
2. **Decentralization**: Extension authors can develop and publish their packages independently without ever needing to modify the core ArmoniK CLI repository or a central list of plugins.
3. **Superior User Experience**: The user workflow is simple and familiar: `pip install` to add, `pip uninstall` to remove. There are no extra steps to enable or disable a plugin.
4. **Robustness and Performance**: The implementation includes features to ensure the core CLI remains stable and fast, regardless of the number or quality of installed extensions.

### Implementation Details

The core of the extension system relies on the following concepts:

- **Entry Point Group**: All ArmoniK CLI extensions must register their main command object under the entry point group named `armonik.cli.extensions`.
    
- **Lazy Loading**: To ensure fast startup times, extensions are **not** loaded when the CLI starts. The CLI only reads the names of the registered extensions. The actual Python module for an extension is only imported into memory at the moment a user invokes its command (e.g., `armonik my-extension-command ...`). This prevents a broken or slow extension from impacting the usability of the core CLI or other extensions.
    
- **Error Handling**: If an extension has a syntax error or any other issue that prevents it from being imported, the main CLI will not crash. Instead, it will register a "Broken Extension" command. When the user tries to run this command, they will be shown a detailed error traceback, clearly indicating which extension is faulty and why. This makes debugging significantly easier for both end-users and extension developers.
    
- **Extension Introspection**: To improve discoverability, the ArmoniK CLI provides a dedicated command to manage extensions:
    
    Bash
    
    ```
    armonik extensions list
    ```
    
    This command lists all installed extensions, the package they came from, their version, and their status (e.g., "OK" or "Broken").
    
- **Configuration Management**: All extension configurations should be centralized within the main ArmoniK configuration file under a top-level `plugins` key. The core CLI will be responsible for parsing this configuration and making the relevant section available to each plugin, ensuring a single, consistent source of truth for settings.

## Extension Guidelines

This section provides a practical guide for community members who wish to develop an extension for the ArmoniK CLI.

### 1. Packaging your Extension

Your extension must be a standard, installable Python package. The most important part is the `pyproject.toml` file, which must declare the entry point.

**`pyproject.toml` Example:**

```toml
[project]
name = "armonik-cli-ext-hello"
version = "0.1.0"
requires-python = ">=3.10"
# Extensions should depend on the core library, not the main CLI application.
dependencies = [
    "armonik-cli-core",
    "rich-click" # Better keep this version vague so as to use the same version as in armonik-cli.
]

[build-system]
requires = ["setuptools", "wheel"]
build-backend = "setuptools.build_meta"

# This section is mandatory for discovery.
[project.entry-points."armonik.cli.extensions"]
# 'hello' is the command name that will appear in the CLI.
# 'armonik_cli_ext_hello.cli:hello_command' points to the Click object to load.
hello = "armonik_cli_ext_hello.cli:hello_group"
```

For easier discoverability of extensions, we (strongly) recommend the naming convention `armonik_cli_ext_<your-extension-name>`.

### 2. The Command Object

The entry point must point to an instance of `click.Command` or `click.Group`.

**`armonik_cli_ext_hello/cli.py` Example:**

```python
import rich_click as click

# 'main' is the click.Group object referenced in pyproject.toml
@click.group()
def hello_group():
    """
    A hello world extension for the ArmoniK CLI.
    The docstring of a group is used as its help text.
    """
    pass

@main.command()
@click.option('--name', default='World', help='The name to greet.')
def say(name):
    """Prints a greeting."""
    click.echo(f"Hello, {name}!")
```
